## JSON/history clarification and outstanding design question

The user questioned unnecessary disk reads/writes and retaining temporary
state/all completed history. An earlier misunderstanding was corrected:
**the server does store JSON on its local disk**, although it is not browser
state. Do not describe the system as having no local JSON.

- Workspace/result discovery scans real directories, not job history. A job
  record does not prove its result files still exist.
- Server-side `jobs.json` retains queue/acceptance and job state for restart
  recovery, idempotency and recorded completion/convergence.
- Removing that durable ledger or all completed history has **not** been
  implemented. Hiding history in CLI output does not delete it. Current source
  still retains completed records.
- Deletion-progress RAM management is an unreleased change; published v1.7.2
  still performs the older journal updates.
- `conditions.json` describes analysis/rendering conditions; `run-inputs.json`
  records provenance per result, not per field file. These differ from the
  private job ledger. Console command history stays in session memory.

Restart recovery and acceptance guarantees require some durable storage if
retained. Temporary progress/display state does not. Further reduction of
finished history/journal retention remains a design consideration, not a
completed change or an instruction to discard all persistent state.
